## R1. 災害情報を「行動指示」に変換して出す

### 現状

| 実装 | 場所 | 言語 | 中身 |
|------|------|------|------|
| 気象警報の行動指示（コード別） `WARNING_GUIDANCE` | `backend/app/services/warning_service.py:103` | ja / en | コード別の細かい行動指示 |
| 気象警報の行動指示（グループ別） `HAZARD_ACTION` | `backend/app/services/warning_guidance.py` | **16言語**（2026-07-30 追加） | 災害種別13グループ + 特別警報の接頭語 |
| 警報の**名前** `WARNING_NAMES` | `backend/app/services/warning_names.py` | **16言語**（2026-07-30 追加） | 災害種別18語 × 警報レベル3語の合成 |
| 説明文テンプレ `DESCRIPTION_TEMPLATES` | 同上 | **16言語**（2026-07-30 追加） | — |
| **地域名** `AREA_TRANSLATIONS` | `backend/app/services/warning_service.py` | **4地域 × 5言語のみ** | ⚠️ 未登録の地域は**全言語で日本語のまま**（都道府県は47件） |
| 震度の説明 `descriptions` | `frontend/src/components/IntensityGauge.tsx:38` | 16言語 | **行動指示ではなく体感の記述**（「立っていられない」「投げ出される」） |

### ギャップ

1. ~~**`WARNING_GUIDANCE` が 2 言語しかない。**~~ → **2026-07-30 対応済み。** `backend/app/services/warning_guidance.py` を新設し、**災害種別13グループ × 16言語**の行動指示を用意した。特別警報には「命に関わる危険」の接頭語を付ける。ja / en のコード別文面は従来どおり優先されるため既存挙動は劣化しない。
   - **前回の記述の訂正**: 実行時は `guidance.get(lang, guidance.get("en", ""))` で**既に英語へフォールバックしていた**。したがって本件は「日本語が出ていた」のではなく「**14言語が英語だった**」が正確。深刻度は当初の記述より低い。
   - **設計上のトレードオフ（意図的）**: 29コード × 16言語 = 464 文面を無レビューで量産するリスクを避け、13グループ × 16 = 208 に抑えて一つ一つ丁寧に書いた。災害種別の細かいニュアンス（例「除雪時の事故」）は落ちる。コード別に増やしたくなったら `WARNING_GUIDANCE` に言語キーを足せばグループより優先される。
   - 併せて軽微な齟齬: README / CHANGELOG は「28 種類」と記載しているが、辞書の実測は **29 種**。

   **警報名も 2026-07-30 に16言語化した** → `backend/app/services/warning_names.py`。29コード × 16言語を並べる代わりに「**災害種別18語 × 警報レベル3語 + 言語ごとの語順**」の合成方式にした（語順の例: ja「大雨警報」/ vi「Cảnh báo mưa lớn」/ fr「Alerte : fortes pluies」）。
   - **既存6言語の文面は1文字も変えていない**。移行前の29コード分の文面をテストに凍結し、合成結果と全件突合している（`TestNoRegression`）
   - 説明文テンプレも16言語化済み

   **⚠️ 未対応で残る本体**: **地域名**（`AREA_TRANSLATIONS`）が **4地域 × 5言語**しか登録されておらず、未登録の地域は `area_trans.get(lang, area_name)` により**全言語で日本語のまま**表示される。都道府県は47件あるため、実際にはほとんどの地域名が日本語で出る（英語ユーザーも同様）。「どこに何の警報が出ているか」の「どこ」が読めない状態で、警報機能で残る最大の穴。
2. **`IntensityGauge` の `descriptions` はソース上のコメントが「直感的な行動指示」だが、実体は現象の描写。** 「震度6強 = 這わないと動けない」は状況説明であって、訪日客が知りたい「だから今どうすべきか」ではない。
3. ~~**`safety_guide._get_fallback()` が日本語ハードコード。**~~ → **2026-07-30 対応済み。** `backend/app/services/safety_guide_fallback.py` を新設し、**16言語**の静的フォールバックに差し替えた。未対応言語は日本語ではなく **`en`** に落とす（読めない人に読めないものを返さないため）。レスポンスに `fallback` フラグを追加し、静的ガイドか AI 生成かをクライアントが判別できるようにした。
   - モジュールは**外部依存ゼロ**なので、停電・低回線・APIキー未設定のいずれでも動く（R2 とも両立）
   - 回帰テスト 218 件追加（backend 86 → **304 件**）。旧実装に戻すと12件 fail することを確認済み

### 対応の方向

- ~~`WARNING_GUIDANCE` を 16 言語化~~（2026-07-30 完了）
- ~~`WARNING_CODES`（警報名）と `DESCRIPTION_TEMPLATES` を 16 言語化~~（2026-07-30 完了）
- **`AREA_TRANSLATIONS` を整備**（現状 4 地域 × 5 言語。未登録は全言語で日本語のまま）
- `descriptions` とは別に「震度 → 取るべき行動」の辞書を新設
- ~~`_get_fallback()` を言語別の静的辞書に差し替え~~（2026-07-30 完了。`safety_guide_fallback.py` の
  `SAFETY_GUIDE_FALLBACK` が上記2件の雛形になる — 依存ゼロの静的辞書 + 未対応言語は `en` に落とす方針）

## R2. 停電・低電力・低回線で動く

### 現状

`frontend/public/sw.js` の実測:

| 対象 | 戦略 | 場所 |
|------|------|------|
| 静的アセット | cacheFirst | `sw.js:84-85` |
| `/api/**` | **networkFirst（キャッシュへフォールバック）** | `sw.js:86-87` |
| 地図タイル（GSI / OSM） | cacheFirst + 7日有効 | `sw.js:88-89` |
| プリキャッシュ対象 | `/`, `manifest.json`, `offline.html`, アイコン2枚 | `sw.js:9-15` |

→ **一度でも開いていれば、オフラインでも直近の災害情報と地図タイルが読める。** これは R2 の中核が満たされている。

### ギャップ

1. **初回訪問がオフライン/低回線だと何も出せない。** プリキャッシュに避難行動の静的コンテンツが含まれていない（`sw.js:9-15`）。災害発生後に初めて開くユーザーがまさにこのケース。「電波が無くても読める最小限の行動指示」を静的資産としてプリキャッシュすべき。
2. **省電力設計が無い。** `prefers-reduced-motion` の対応のみ（`frontend/src/app/globals.css:188`, `frontend/public/offline.html:134`）。バッテリー残量に応じた低電力モード（地図・SSE・ポーリング停止、白背景を暗色へ）は未実装。停電で充電できない 67% に対して、**アプリ自体が電池を食う側**になっている可能性がある（実測はしていない = 未検証）。
3. **SSE 常時接続が電力・通信を消費し続ける。** `/api/v1/events/stream` は 10 秒ポーリング + 30 秒ハートビート。低電力時に切る導線が無い。

### 対応の方向

- 「オフライン最小行動ガイド」を全言語ぶん静的生成しプリキャッシュ
- Battery Status API（対応端末のみ）または手動トグルで低電力モード
- 低電力モードでは SSE を切り、ポーリング間隔を延ばす

## R3. インストール・事前設定なしで即使える

### 現状

- Web アプリなので **URL 1本で即利用可能**。Safety tips（アプリ）に対する構造的な優位。
- PWA インストールは任意（`InstallBanner.tsx`）で、必須ゲートではない。
- 位置情報は避難所表示時にのみ要求（`frontend/src/components/ShelterMap.tsx:397-405`）。初回表示のブロッカーになっていない。

### ギャップ

1. ~~**初期表示言語が日本語固定。**~~ → **2026-07-30 対応済み。** `frontend/src/i18n/detectLanguage.ts` を新設し、保存済みの明示選択がなければ `navigator.languages` から表示言語を推定するようにした（該当なしは `en`、`easy_ja` は自動選択しない）。併せて、SSR 既定値の `'ja'` を「利用者の明示選択」として localStorage に書き込んでしまう不具合も修正した（これがあると次回以降も推定が効かない）。
   - 実ブラウザでの before/after 実測（production build + Chrome `--lang`）:

     | `--lang` | 修正前 | 修正後 |
     |----------|--------|--------|
     | en-US | `lang=ja` / 災害対応AI | `lang=en` / Disaster AI |
     | ko-KR | `lang=ja` / 災害対応AI | `lang=ko` / 재난대응AI |
     | th-TH | `lang=ja` / 災害対応AI | `lang=th` / AI รับมือภัยพิบัติ |
     | zh-TW | `lang=ja` / 災害対応AI | `lang=zh-TW` / 災害應對AI |

   - 残る制約: SSR は `ja` を返すため、**クライアント JS が動くまでの一瞬だけ日本語が見える**。完全に消すには middleware で `Accept-Language` を見て言語別に配信する必要があり、別途判断。
2. **宿泊施設・観光案内所経由の配布導線が無い。** 実際に役立った情報源1位は「宿泊先の従業員」30.3% だが、QR コードや印刷用ページ（`@media print`）は未実装（grep でヒットなし）。ホテルのフロントに貼れる掲示物が無い。

### 対応の方向

- ~~`navigator.language` / `Accept-Language` による初期言語の自動判定~~（2026-07-30 完了）
- 掲示用の QR + 印刷ページ（多言語）を用意し、宿泊施設に配れる形にする

## R4. 交通・旅程の見通しを示す ❌ 未実装

### 現状

`backend/app/services/` の全 15 ファイル（`__init__.py` を除く 14 サービス）を確認したが、**交通・鉄道・空港・フライトのデータ源は一切ない**。

```
ai_provider / event_manager / jma_service / location_translations / p2p_service /
push_service / safety_guide / shelter_service / translation_cache /
translation_templates / translator / tsunami_service / volcano_service / warning_service
```

`運行情報|鉄道|railway|odpt|flight|airport|transit` の grep はゼロ件。

### ギャップ

ニーズ側では **日程崩壊 37.3%（全体4位）・今後の日程 27.0%（7位）・交通と空港の情報 22.2%（9位）** と上位に集中しており、さらに希望する対応でも「交通・飛行機の情報など説明できる案内所」25.4% が入る。**現状のアプリはこの需要にまったく応えていない。**

観光庁の中間報告が指摘する「気象情報や交通情報は主体ごとに発信され一元的に把握できない」という公的課題の、まさに中心がここ。

### 対応の方向（要調査）

- 公共交通の運行情報 API（公共交通オープンデータ協議会 / ODPT 等）の利用可否とライセンスを調査
- 空港の運航情報の一次ソースを特定
- 最小実装としては「災害時に確認すべき交通の公式リンク集を言語別に出す」だけでも空白は埋まる

## R5. SNS で平時に認知を取り、デマに反証する ❌ 未実装

### 現状

`frontend/src/app/layout.tsx` の OG メタ:

| フィールド | 値 |
|-----------|-----|
| `title` | `災害対応AI - Disaster Response AI` |
| `openGraph.title` | `災害対応AI - Japan Disaster Alert` |
| `openGraph.description` | `16言語対応のリアルタイム災害情報システム` |

### ギャップ

1. **OG メタが日本語主体。** SNS でシェアされた瞬間に外国人へ提示されるカードが日本語で、想定ユーザーに刺さらない。16 言語対応を謳いながら、SNS 上の第一印象は日本語。
2. **共有機能が無い。** `navigator.share` / シェアボタンの実装なし。役立った情報源に「日本にいる外国人の SNS 書き込み」23.8% が入っているのに、**ユーザーが他の旅行者へ拡散する導線が無い**。
3. **デマへの反証コンテンツが無い。** 2025 年の「7月5日」デマで香港が 33% 減という実害があり、気象庁は「日時を特定した予測は科学的に不可能」と明言している。この種の**公式見解を多言語で即座に提示する枠**が無い。JNTO の SNS が 2 言語しかない空白は、ここで埋められる。

### 対応の方向

- OG メタを英語基調にし、言語別 OG（動的 `generateMetadata`）へ
- 「この情報は気象庁の公式発表に基づく」ことを明示する出典表示 + シェア導線
- デマ検証セクション（公式見解の多言語提示）

## 未検証の項目

- アプリ自体の消費電力は**実測していない**。R2-2 の「電池を食う側になっている」は仮説である。
- 交通情報 API のライセンス・商用可否は未調査。
- Safety tips の実際の利用率が不明なため、「Web の方が届く」は理屈としては成り立つが**データによる裏付けはない**。
